# PearPlay control contract v1

Native Messaging is control only. Media is fetched directly by the receiver; no relay or cookies are transferred. This contract is shared by `extension/` and `helper/`. Changes incompatible with v1 require a new version, not silent field reinterpretation.

## Framing and trust

Native Messaging uses a native-endian unsigned 32-bit byte-length prefix followed by UTF-8 JSON. Each message is at most 65,536 bytes. Reject invalid lengths, malformed JSON, unsupported versions, unknown operations, unexpected keys and invalid field types. Host name: `com.pearplay.helper`. Installation allowlists an exact `[a-p]{32}` extension ID; the runtime independently checks the exact `chrome-extension://ID/` origin. No wildcard origins.

## Requests

Every request has exactly `v`, `id`, `op`, `args`:

- `v`: integer `1` (not boolean).
- `id`: 1–64 ASCII letters, digits, underscores or hyphens.
- `op`: `hello`, `discover`, `start`, `status`, `stop`, `pause`, `resume`, `pair_begin`, `pair`; the unreleased opt-in firewall extension below adds `firewall`.
- `args`: object, constrained below.

| Operation | Arguments |
|---|---|
| hello, status, stop, pause, resume | `{}` |
| discover | `{}` or `{ "host": "literal IPv4 or IPv6 address" }` |
| pair_begin | `{ "receiver": "discovered identifier", "host": "literal IP" }` |
| pair | `{ "receiver": "discovered identifier", "host": "literal IP", "pin": "4 digits" }` |
| start | `{ "receiver": "discovered identifier", "host": "literal IP", "url": "exact HTTP(S) URL" }` |

URLs are bounded to 16,384 characters. Preserve original text, including percent escapes, case, query order and fragment. Reject whitespace, controls, backslashes, missing host, credentials in authority and invalid ports. Never put real media URLs in argv, source, logs, reports or persistent browser storage. A parsed URL may be used for validation and a hostname-only display, never as a normalized replacement for the original.

`start` requires explicit candidate and receiver selection. Receiver host is a discovery hint, not an override of paired identity. This prototype may support one paired receiver at a time. If Send needs pairing, PearPlay starts pairing first so the Apple TV displays the PIN, then the popup asks for those 4 digits in a masked field. The extension does not store the PIN. Stored credentials still never leave `~/.local/state/pearplay/`.

## Responses and events

Responses contain `v: 1`, matching `id`, `ok` (boolean), `state`, `evidence`, and `capabilities` (operation strings). Since helper 0.2.0, responses also include optional `helperVersion` (bounded `major.minor.patch`); older v1 responses remain parseable, and setup asks for an update when required features or the minimum helper version are missing. Optional `receivers` is a bounded array of `{identifier,address,label}` with optional `kind: "apple-tv" | "airplay-video"`. Kind is based on advertised model/video features, not verified playback; `airplay-video` must display compatibility unverified. Unknown kinds retain a generic receiver label. Linux discovery merges multicast and resolved Avahi advertisements; audio-only and screen-mirroring-only advertisements are excluded. Discovery is bounded to 20 seconds in the helper and 25 seconds in the extension, with `discovery_failed` distinguishing a failed scan from a successful empty scan; optional `error` is a static sanitized error code. Never forward upstream exception text, arbitrary device properties, raw URLs or protocol payloads. Asynchronous state notifications use `id: "event"`.

States: `idle`, `connecting`, `playing`, `paused`, `stopping`, `stopped`, `error`.
Evidence: `none`, `protocol`, `unverified`.

HTTP acceptance alone must not become `playing`. A validated receiver playback event can yield `playing` with `evidence: "protocol"`; it is still not proof of visible video or audible sound. A stop command accepted without receiver confirmation must retain unverified evidence. Disconnects invalidate pending operations and expose an error/recovery state. Capability advertisement must not imply controls have been human-verified.

## Unreleased firewall and playback-diagnostic additions

These source changes are not in helper 0.2.5 or the published Store extension.

- `firewallSupport: true` advertises the optional `firewall` request without changing the legacy `capabilities` list: older Store clients reject unknown capability strings. New clients must not send it to older helpers.
- Arguments are exactly `{receiver, host, action}`; `action` is `check`, `allow` or `remove`. Host must be a canonical RFC1918 IPv4 address matching that discovered receiver. The extension derives it from the selected receiver, never from a webpage. Setup tabs and content scripts cannot request changes.
- `check` reads saved UFW configuration only. Result field `firewall` contains `supported`, nullable `enabled`, `allowance: present|missing|unknown`, and `owned`. These fields do not establish loaded kernel rules or packet delivery.
- `allow`/`remove` require explicit popup consent and normal desktop administrator approval through pkexec. Only the selected source IPv4 and UDP destination port 49170 are eligible. No installer rule, global allowance, firewall enable/disable or DNS change is permitted. Removal is limited to unambiguously PearPlay-owned rules.
- Optional nested `change: {ok, error?}` reports the mutation separately from playback state. Error strings are from a fixed allowlist; raw stderr is never forwarded. The worker retains the result while its native connection stays alive so reopening after desktop authentication can show it. Requests have a 140-second browser deadline around the bounded 120-second authorization call; other native actions are held off during mutation.
- The packaged CLI recognizes exactly `firewall-privileged <action> <host>`. The module validates frozen root-owned installed identity and pkexec caller before mutation. Source/extracted builds cannot authorize themselves as an installed privileged helper. This path still requires a real Linux packaged permission/rollback rehearsal before release.
- Playback failures may include `diagnostic: {stage, reason, httpStatus?}`. Stage and reason use fixed allowlists and status is an integer 100–599. No PIN, credential, stream URL, response body, or exception text is included. Diagnostics identify a failure boundary, not proof of TV compatibility.

## Unreleased no-PIN V1 additions

These additions are a candidate implementation, not a published helper or Store release. Keep all v1 request schemas, state/evidence enums and operation capability strings unchanged; older clients reject unknown enum/capability values.

- Unpaired receivers may use V1 URL sending only after fresh exact identity/address resolution and affirmative, consistent advertised video/auth properties. Missing properties defaulting to NotNeeded/V1 in pyatv are not eligibility proof. Require NotNeeded, no password, Null credentials and Auto-selected V1; reject contradictory aliases and unsupported access settings. A matching saved pairing retains the authenticated command path and must never downgrade to no-auth V1. No protocol fallback after a failed cast. V1 never creates or overwrites pairing credentials.
- Optional receiver `timingRequired: false` is advisory: this positively classified no-auth route needs no timing UDP listener. Missing metadata means unknown/legacy behavior, not false. The helper must revalidate at Send; cached discovery does not authorize transport. New clients skip automatic timing-rule checks/Allow prompts for this route but preserve explicit saved-rule inspection and removal of a verified owned rule. Never change firewall policy automatically.
- After V1 `/play` HTTP200, retain legacy `state: "connecting"`, `evidence: "unverified"`. Optional `session` is exactly `{receiver, host, transport: "airplay-v1", delivery: "accepted", timingRequired: false}`. Receiver is a bounded nonempty identifier (maximum 1024 characters), host a literal IP. It identifies the active send, not a later dropdown selection; it contains no media URL. New clients accept it only on successful connecting/unverified replies, discard malformed/unknown-field session objects, and render “Sent to TV — check the picture and sound.” They do not show Playing or an endless working indicator. Older clients ignore the extra field and retain Connecting; they remain wire-compatible but do not gain the improved wording.
- Include active session metadata consistently in status/hello/discovery responses while the hold remains active; clear on fresh start, stop, error, peer close and native disconnect. Do not retain stale metadata across replies that omit it. A duplicate Send cannot create another V1 session or destroy the accepted state. End helper session remains available. Neither acceptance nor socket closure proves TV playback/completion; socket closure ends the local session with unverified evidence, and must release resources/lease without polling the receiver or automatically recasting.
- An unsupported unpaired route uses the existing `transport_failed` envelope with optional `receiverIssue: "unsupported_access" | "incomplete_advertisement" | "unsupported_protocol"`. New clients show static access/discovery/mode guidance and do not ask for a fictitious PIN. Ignore unrecognized reason text. Preserve the allowlisted reason with the existing preserved error on successful status/hello/discover refresh; a new attempt/event clears it. Mandatory-PIN receivers keep the existing flow.
- Existing command-path playing notifications and PIN handling retain their meaning. No V1 pause/resume or confirmed Stop TV capability is advertised. Source, frozen/browser, watched playback, lifecycle and paired-route regressions are distinct acceptance gates; diagnostic success is not release readiness.

## Local playback and recovery

Do not automatically pause local playback on command acceptance. The prototype uses explicit user confirmation of TV video/audio before pausing the specifically selected local video. Local resume remains available after errors or native disconnection. Navigation invalidates previous document candidates and must not pause a replacement page's video.

## Setup and multiple browsers

The local extension setup page may request only a helper handshake and explicit receiver discovery through its worker interface; playback, pairing, website access and installation are not granted to this page. Only its exact top-level extension URL is accepted. First-run setup opens on installation, not on routine updates.

A packaged helper pins one exact extension origin at build time and is registered separately with each supported browser. It shares per-user pairing storage. A filesystem lease excludes simultaneous transport and PIN pairing across helper processes. A busy browser cannot terminate a different browser’s session; stop only closes its own transport. Disconnecting a browser’s registration preserves credentials and the shared payload.

## Compatibility gate

Automated contract tests and protocol events are separate from browser integration and human TV observations. Full prototype acceptance requires Chrome and Brave individually, FOX video/audio through this integration, an actual observed ad/program transition with Pi-hole blocking temporarily disabled, and lifecycle/error/uninstall evidence. No elapsed-time or mock result substitutes for these observations.
